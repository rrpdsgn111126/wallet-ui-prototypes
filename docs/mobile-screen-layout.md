# mobile-screen-layout.md — канонические UI-паттерны прототипа alt.vu

**Обновлено:** 2026-11-13. **Единственный рабочий прототип:** `transfi-remittance/index.html`; банковский поток: `transfi-remittance/legacy.html`; offline-события и история: `transfi-remittance/preview-interactions.js`.

Документ фиксирует **паттерны визуальной сборки и переходов**, а не действующие правила TransFi API. При расхождении со скриншотом эталоном служит текущий исходный экран alt.vu из Google Drive и исходная разметка в `index.html`, а не самостоятельная переработка UI Kit. Не вводить второй набор компонентов для SEPA/SWIFT.

## 1. Оболочка и навигация

- Использовать `.view`, `.tint`, `.wrap`, `.head .back .h1`, `.foot .btn` / `.btno`; для панели методов — исходную `.sheet`, `.m` и `.dim`.
- В исходном кошельке один USD-баланс. С экрана «Главная» пользователь выбирает «Пополнить» / «Вывести», затем метод; KYC обязателен для **всех** способов пополнения, вывода и переводов. Offline-макет использует верифицированную тестовую учётную запись, не обходит правила боевого приложения.
- После закрытия банковского iframe возвращаться на исходный выбор метода; не создавать вторую «главную».
- Обязательный экран проверки перед подтверждением исходящего перевода; возврат на предыдущий шаг сохраняет введённые реквизиты.

## 2. Поля суммы (`amount`)

**Источник:** `components/amount.html`, исходный `#v-out-usdt-tron .wd-amt` и общий CSS `css/alt-vu-wallet.css`.

- Наружный контейнер `<div class="fld w">` с `.fi` (иконка монеты), `.fl` (подпись «Сумма перевода» + `<b><input class="wd-amt" inputmode="decimal"></b>`), `.addon` (валюта и `.mx` / MAX).
- Для SEPA/SWIFT пользоваться тем же рисунком и структурой, допускаются только ограниченные селекторы `.tf-amount` и `.tf-max`. Не добавлять отдельный большой числовой экран и параллельную стилизацию.
- Ввод: цифры, одна десятичная точка / запятая; запрет отрицательных сумм. MAX = доступно минус комиссия, если комиссия списывается дополнительно. Не превышать баланс; ошибка показывается `.fld.err` и короткой подписью, не только toast.
- Нельзя называть комиссию частью суммы получения без соответствующего расчёта. В **демо** исходящая сумма `amount` означает сумму отправки, комиссия списывается сверху: списание = сумма + комиссия, получение = сумма × FX. Курс демонстрационный и не подтверждён API.

## 3. Таблица курса / комиссии

**Источник:** `components/tbl.html` и карточка деталей операции в `#v-details`.

- Единственная структура для расчётной таблицы — `<div class="tbl"><div class="rl"><span>Название</span><b>Значение</b></div>…</div>`.
- В обоих новых методах показывать «Сумма перевода», «Курс», «Комиссия», «Списать всего», «Получит». В исходящих вариантах использовать `.tbl.tf-quote`; одинаковая разметка на шаге суммы и на экране проверки.
- Значения выравниваются по правому краю, длинные SWIFT-значения переносятся, стиль фона/радиусов/разделителей наследуется от оригинальной `.tbl`. Нельзя заменять таблицу независимыми `.box .row .rt/.rv`.
- Условные значения FX и fee в статическом макете не выдавать за реальные комиссии, не выполнять транзакции.

## 4. Селектор страны

- Оригинальная `.fld w` с открытием исходного паттерна нижнего селектора `.sheet`; показывать **круглый флаг** выбранной страны, её название и chevron. Для каждой строки списка — флаг, название, текущий выбор.
- Текущая реализация: `uxPickerField('Страна получателя','country','country')`, `uxFlagPlate()`, `uxRenderPicker()`.
- В SEPA ограничивать список поддерживаемыми в макете SEPA-странами; в SWIFT показывать настроенный список, не имитировать несуществующий полный справочник всех стран. Доступность реального маршрута определяет API/MID.
- Ввод пользователя сохраняется, пока не изменены условия, при которых текущий способ становится недоступен.

## 5. История и карточка деталей

- Историю рисовать исходным `groupOps()` / `.op[data-id]`, а детали — **только** исходным `openOp(operation)` / `#v-details`. Не создавать самодельную «карточку операции» поверх общей истории.
- Строка операции на главной должна быть кликабельной по всей площади; `Enter` / `Space` с клавиатуры открывают те же детали.
- Использовать синтетические записи с уникальными `id`; статус, сумма, монета, сеть, реквизиты и время берутся из той же записи, а не из текста строки.
- SEPA/SWIFT исходящие передают offline callback из iframe через `postMessage`. Родитель принимает сообщения только от **текущего iframe того же origin**. Одна операция — один ID: переходы `pending → success/failed/held` обновляют запись, не дублируют строку истории.
- Для **входящих** SEPA/SWIFT счёт показывает реквизиты; сумма неизвестна до вебхука. Поэтому статусный экран тестируется отдельно, без выдуманного зачисления в историю или к USD-балансу.

## 6. Завершение операций и callbacks

- Исходящий перевод: метод → сумма → получатель → проверка → подтверждение/PIN (если исходный метод требует) → обработка → успех / ошибка / дополнительная проверка.
- USDT/USDC, ALT.VU, СБП: максимально сохранять **оригинальные** экраны, сетевые пикеры, адреса/QR, ПИН, финальные статусы и операционные детали. Реальные внешние обращения запрещены в static preview.
- Offline QA `?qa=1`: `Следующий результат` = успех / ошибка / в обработке; callback для криптопополнения, СБП и отдельно SEPA/SWIFT; завершение ожидающей операции. Тестовые кнопки — **за пределами экрана телефона**, а не под основным CTA.
- После callback история обновляется, новые операции доступны с главной. Ошибка не списывает USD; если заранее зарезервировано списание и затем получен fail, тестовый остаток восстанавливается.
- Не использовать реальных реквизитов, реальных checkout-ссылок и настоящего QR-кода оплаты. Демо-адреса должны быть помечены как нефункциональные.

## 7. Регрессионная проверка

- Оригинальные сценарии и клики: `python tests/bank-qa/source-flows.py` (Playwright/Chromium).
- Банковские страницы, ввод, финальные статусы: `node tests/bank-parity.mjs`, `python tests/bank-qa/smoke.py` (Playwright).
- Размеры экрана 390/430; не должно быть горизонтального скролла и ошибок JS. Проверять всю строку истории, откуда открываются детали, значение суммы / MAX, флаг и picker страны, 5 строк таблицы, отказ и возврат.
- GitHub Actions: `prototype-playwright.yml`, `transfi-bank-parity.yml`, `transfi-source-playwright.yml`; публикация в `main` проходит GitHub Pages.

**Граница достоверности:** офлайн-прототип демонстрирует UX-переходы; реальные реквизиты, комиссия, статус провайдера, KYC и расчёт конвертации должны поступать с backend. Никакой mock callback не считается реальным платежом.
