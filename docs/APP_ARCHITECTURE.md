# alt.vu — карта приложения и руководство по сборке экранов

> **Канонический прототип — решение от 2026-11-13:** `../transfi-remittance/index.html` (банковские сценарии в `../transfi-remittance/legacy.html`). Отдельные прототипы версий удаляются; UI Kit проверяется по текущему прототипу, а не наоборот.

> **Статус:** рабочая реконструкция по PNG-макетам и библиотеке HTML/CSS. **Не** утверждённая продуктовая спецификация и **не** описание реализованного backend/API.  
> **Дата анализа:** 2026-11-11; **подтверждения бизнес-правил:** 2026-11-12. **Библиотека:** снимок веб-сборки от 2026-11-10 18:18, исходный коммит `ae501917`.  
> **Платформы:** веб-кошелёк / мобильный web / PWA-контекст; отдельно Telegram Mini App. Native iOS/Android **не входят** в библиотеку.

## 0. Цель и критерии приёмки

Цель — дать дизайнеру, разработчику и AI-агенту ориентир, как собирать интерфейсы из `components/*.html`, согласовывать их с PNG и не домысливать продуктовую логику.

Результат считается пригодным **для прототипирования**, если:
1. Новый экран имеет источник PNG, название, точку входа, состояния, переходы и состав компонентов.
2. Для каждого переиспользуемого элемента указан реальный путь `components/<id>.html`; отсутствующие элементы помечены как новые.
3. В светлой/тёмной темах используется существующая система CSS, а не произвольно созданные стили.
4. Реальные бизнес-ограничения, роли, статусы, суммы и API **не выводятся** из демонстрационных значений на PNG.
5. Неизвестные решения оформляются как вопросы/допущения, а не как готовые требования.
6. Результат проверяется на 390 и 1440 px, с загрузкой ресурсов и без ошибок JavaScript; для состояний есть скриншоты или иная проверяемая фиксация.

**Легенда достоверности:** **[PNG]** — виден на макете; **[LIB]** — представлен в библиотеке; **[INFER]** — реконструкция пользовательского перехода, требующая проверки; **[OPEN]** — продуктовый вопрос не разрешён. Названия возможных маршрутов ниже — **смысловые идентификаторы документа**, не фактические URL.

## 2. Информационная архитектура

### 2.1. Общая схема [PNG + INFER]

~~~text
Вход в продукт
├── Регистрация: email → код → имя → создание/повтор PIN → готово
├── Вход существующего пользователя → подтверждение → PIN/сессия
└── Необязательная / отложенная подготовка к карте
    ├── Телефон → SMS/Telegram-код
    ├── Страна проживания → документ → проверка KYC
    ├── Пополнение доступного остатка
    └── Выпуск карты → ожидание → карта готова

Авторизованный кошелёк
├── Главная (баланс, карта/заглушка, быстрые действия, история, баннер)
│   ├── Пополнить
│   │   ├── СБП → банк → RUB/курс → приложение банка → ожидание → результат
│   │   ├── USDT / сеть → QR и адрес → отслеживание зачисления
│   │   ├── USDC / сеть → QR и адрес → отслеживание зачисления
│   │   └── ALT.VU → внутренний перевод [наличие пункта по макетам]
│   ├── Вывести
│   │   ├── USDT / сеть → адрес и сумма → проверка → PIN → статус
│   │   ├── USDC / сеть → адрес и сумма → проверка → PIN → статус
│   │   └── ALT.VU → поиск получателя → сумма → проверка → PIN → готово
│   ├── Заработать → партнёрская программа
│   ├── История → фильтры / детали → квитанция
│   └── Карта → выпуск / управление / тарифы / лимиты / пластик
├── Профиль → данные / настройки / адресная книга / безопасность
├── Уведомления / поддержка
└── Установка приложения (PWA-подсказки)

Telegram Mini App [отдельный контекст]
├── Приветствие / связь с Telegram / существующий аккаунт
├── PIN / блокировка / повторное создание / отвязка
├── Главная, профиль, партнёрка
└── KYC / статусы / операции — доступность уточняется
~~~

**Навигация:** в `components/bnv.html` есть нижнее меню из **«Главная / Пополнить / Карта / Вывести / Профиль»** [LIB]. Однако PNG демонстрируют и варианты с быстрыми действиями без постоянно видимого нижнего меню. Универсальное правило показа навигационной панели **не подтверждено** [OPEN]. Профиль на некоторых экранах открывается нажатием на имя/аватар; уведомления и поддержка — отдельными кнопками в шапке [PNG].

## 3. Каркас и композиция экранов

1. **Типы экранов:** главная с собственной шапкой и крупной карточкой; стандартный экран с «назад» и заголовком; полноэкранный статус; шторка поверх предыдущего экрана; форма с нижним основным действием; детальная карточка операции. [PNG]
2. **Шапка:** `hdr` для главной, `head` для обычных экранов; кнопки уведомлений/поддержки показаны в шапках отдельных макетов. Вопрос: какие иконки глобальны, а какие контекстны.
3. **Основное действие:** `btn` — лайм, обычно одно доминирующее CTA на экран; `btno` — вторичное; `lnk` — текстовая ссылка. Состояния disabled, ошибка и загрузка не тождественны друг другу.
4. **Плиты/строки:** `rows`, `tbl`, `fld`, `amount`. Значение, подзаголовок, иконка, статус и правая стрелка имеют семантику; не подменять их произвольными контейнерами.
5. **Шторки:** `sheet`, `netsheet` и их затемнение/handle; контент меняется по задаче. Не все шторки собраны в библиотеке; «выбор банка», фильтры и PIN — разные композиции.
6. **Темы:** светлая — переменные на `.phone`, тёмная — `html.dark`. Тестировать обе. Не переносить `showcase/specimen.css` и `showcase/states.css` в продукт: это стили демонстрационной витрины.
7. **Ресурсы:** использовать `assets/`; не рисовать логотипы монет/сети вручную, когда существует оригинальный asset. Типографика — Inter из библиотеки.
8. **Responsive:** мобильная ширина и десктопная рамка — разные контексты. Папка `десктоп` показывает центрированную презентацию телефона внутри браузера; она не доказывает наличие полноценного широкого web-layout.
9. **Статусы:** экран загрузки, ошибка, ожидание внешнего действия и успешный результат — отдельные экраны/состояния, а не одна иллюстрация. `done`, `toast`, `warn` и `bdg` помогают их собрать.

### 4.1. Реконструированные сценарии (проверяемые PNG)

**A. Регистрация / онбординг:** email → код → имя → создание и повтор PIN → созданный кошелёк. Отдельный пошаговый сценарий «Три шага до карты»: телефон → код → страна проживания → документ/проверка → пополнение → выпуск → готово. ### 6.1. Несовпадения, которые нельзя «исправлять» по догадке

1. **Главная:** в папке с «ЭТАЛОН» есть тёмное лицо карты; в библиотеке и других листах — лаймовые/зелёные варианты. Нельзя переносить «эталон» на все карточные экраны без решения.
2. **Текущая навигация:** компонент нижнего меню демонстрирует 5 разделов, но на части PNG навигация другая или не показана. Нет подтверждённого правила постоянного отображения.
3. **Тарифы / число карт / выпуск:** среди макетов существуют разные значения, скидки, варианты платёжных сценариев и multi-card. Числа не являются константами приложения.
4. **Веб и Telegram:** сходство экранов не подтверждает равенство фичей, способов входа и доступных операций.
5. **Исторические скриншоты и действующая сборка:** PNG показывают проекты и состояния по датам; `README.md` относится к конкретному снимку CSS. Эти источники не синхронизированы автоматически.

## 7. Состояния и переходы: минимальный контракт для каждого экрана

Для каждого сценария описывать:
- **Entry** — откуда пришли; параметры (тип операции, монета, сеть, recipient ID, card ID).
- **Eligibility** — допустимость действия: KYC, средства, лимиты, доступность метода, платформа.
- **Loading / empty / ready / invalid / submitting / pending / success / failed** — не обязательно все, но явно отметить применимые и отсутствующие.
- **Exit** — «назад», закрытие шторки, отказ, повтор, переход к деталям или на главную.
- **Data** — названия полей, форматы/маски, источник данных, отображаемая валюта, точность и локализация.
- **Effects** — что происходит после CTA: запрос, редирект в банк, PIN, изменение баланса, история; если API неизвестен, обозначить mock.
- **Recovery** — потеря сети, устаревший курс, повторное открытие, двойное нажатие, прерванный платёж, открытие после перезагрузки.
- **Tracking** — события аналитики, если продукту нужны: показ, шаг, ошибка, завершение; сейчас [OPEN].

Предварительная модель операций: `draft → validating → awaiting_confirmation → processing → succeeded | failed | cancelled`. Это **только предлагаемый словарь для проектирования**, не доказанные значения backend. Для СБП отдельно нужны ожидание перехода/оплаты/зачисления; для криптопополнения — ожидается сеть и подтверждения; для P2P — lookup и проверка получателя.

## 8. Указания AI-агенту по сборке прототипов

1. **Зафиксируй основание:** конкретный PNG/папка, дата итерации, желаемая платформа, сценарий и начальное состояние. Если не задано — выбирай самый близкий явно названный референс; неопределённость отметь в README экрана.
2. **Разложи экран на блоки:** status/safe area, header, hero/card, summary, content rows/form, sticky CTA, overlay/modal, feedback. Таблицу «блок → `components/<id>.html` → новый блок» составить **до** верстки.
3. **Сначала композиция:** используй исходные классы и DOM паттерны. Не создавай новые визуальные стили, пока отсутствующий блок не выявлен явно. Для отсутствующего блока сделай отдельный компонент и опиши, почему нет подходящего образца.
4. **Не переноси витрину в продукт:** `showcase/` служит только для демонстрации и не определяет поведение реального кошелька; допустимо использовать существующую HTML-витрину как reference.
5. **Интерактивность прототипа:** все видимые кнопки должны иметь ожидаемое действие (переход, mock state, валидация, закрытие, popup). В прототипе должна быть возможность воспроизвести минимум success, error, loading, disabled и empty там, где они применимы.
6. **Содержимое:** демонстрационные ФИО, адреса, деньги и карты — фикстуры; не размещать реальные пользовательские данные, токены, PAN/CVV или секреты.
7. **Техническая проверка:** локальная витрина; 390 и 1440 px; светлая/тёмная тема; console/pageerror/requestfailed; переполнения, видимость CTA, модальные перекрытия, скролл, клавиатура, изображения/шрифты.
8. **Результат:** исходный PNG, список исходных компонентов, список новых блоков, список известной/предполагаемой логики, скриншоты до/после и нерешённые вопросы. Не утверждать соответствие продакшену только по внешнему виду.
9. **Безопасность репозитория:** развивать только `transfi-remittance/` (канонический UX/UI-прототип); не создавать конкурирующие папки версий. Библиотека `ui-kit/`, `components/` и CSS должны быть согласованы с фактическим отображением этого прототипа. Изменения базовых компонентов и стилей проводить с проверкой регрессий.
10. **Регрессия:** запускать `python3 build/check.py --no-png` при наличии Playwright. Скрипт рассчитан на `file://`; если среда запрещает локальные file-URL, зафиксировать блокировку, а не объявлять тест пройденным. Отдельный тест по HTTP не равен успешному выполнению оригинального скрипта.

### 11.1. Что за продукт и какая у него граница

**[PNG]** Пользователь видит единый кошелёк с денежным балансом в USD; может пополнять его через цифровые активы и СБП, отправлять средства во внешние сети и другим пользователям ALT.VU, выпускать виртуальные и физические Visa, видеть карточные покупки и управлять безопасностью. На главной баланс, карточный интерфейс и история расположены рядом. В истории входящая операция может иметь обозначение USDT/USDC или RUB, а итоговое влияние на кошелёк — USD.

**[INFER]** Главная продуктовая модель — расчётный кошелёк / общий доступный остаток с карточным расходованием, а криптовалюты и СБП выступают способами ввода/вывода средств. Это **не подтверждает** техническую модель хранения, владения криптовалютой, конкретный банк-эмитент или реальную валюту серверного ledger.

**[CONFIRMED, пользователь 2026-11-12]** До успешного KYC запрещены **все пополнения, исходящие переводы и выпуск карт**. Кошелёк и все карты используют **один общий баланс в USD**. Отдельных расходных балансов у виртуальных и физических карт не предполагается. **[OPEN]** Как этот баланс реализован в backend/ledger; как учитываются удержания, резервы, комиссии и партнёрские начисления; как конвертируются входящие USDT/USDC/RUB. Отдельно отображаемый партнёрский баланс не считать вторым расходным балансом: доступность его средств до зачисления требует проверки.

### 11.3. Пользовательские сценарии и правила

#### A. Регистрация → подготовка к использованию → карта

1. **[PNG]** Базовый путь: email → код подтверждения → имя → создать PIN → повторить PIN → кошелёк создан. Начальный «план пути» к карте состоит из телефона, документа и пополнения.
2. **[PNG]** Телефон: страна и номер → код из сообщения. KYC: страна проживания (не тождественна гражданству) → выбор удостоверения → фото/загрузка → «проверяем документы» → результат; в макете упомянут Sumsub.
3. **[PNG]** После KYC сценарий приводит к пополнению на выпуск, а затем к расчёту достаточности средств и списанию платы за выпуск. В листе для примера использованы 25 USD, 100 USD пополнения и 75 USD остатка; **это демонстрационный расчёт**.
4. **[PNG]** Несколько экранов предлагают «Позже», а главная при незавершённом пути показывает продолжение подготовки. **[CONFIRMED]** Пропуск KYC не означает права на пополнение, перевод или выпуск карты.
5. **[INFER]** У аккаунта как минимум разные состояния: создан без проверки; подготовка не завершена; документы на проверке; документы одобрены; денег недостаточно; выпускается карта; карта готова.
6. **[CONFIRMED, пользователь 2026-11-12]** До успешного прохождения KYC **недоступны любые исходящие переводы** (внешний вывод криптоактивов и внутренний P2P) и **выпуск карты**. Это бизнес-ограничение, а не просто disabled-состояние кнопки.
7. **[OPEN/P0]** Можно ли зарегистрироваться и пользоваться главной до KYC, принимать пополнения, просматривать реквизиты, совершать покупки по уже имеющейся карте? Обязателен ли телефон отдельно от KYC? Что происходит при отказе/повторной проверке и неуспешном выпуске после списания?

#### B. Пополнение: сеть / СБП / внутреннее

- **[PNG]** Пользователь выбирает способ: СБП, USDT (несколько сетей), USDC (несколько сетей), ALT.VU. Для криптопополнения показываются сеть, QR, адрес, предупреждение об отправке нужного актива в выбранную сеть.
- **[CONFIRMED]** Криптопополнение недоступно до успешного KYC. **[INFER]** Для сетевого пополнения события: ожидаем поступление → обнаружено в сети → подтверждено → зачислено на доступный остаток. Скриншот адреса **не подтверждает** число подтверждений или AML-логику.
- **[PNG]** СБП: выбор банка / поиск → ввод RUB → расчёт ожидаемой суммы USD и курса → переход в приложение банка → возврат в приложение → «ждём оплату» → зачислено → строка и детали операции. В конкретном макете есть таймер курса, окно оплаты и предупреждение «платите со своего счёта — на своё имя».
- **[CONFIRMED]** Пополнение через СБП недоступно до успешного KYC, как и все остальные пополнения. **[OPEN/P0]** В какой момент фиксируется FX-курс? Что при изменении курса, частичной оплате, оплате с чужого счёта, двойном возврате из банка, истечении таймера, отмене, отказе банка и позже пришедших деньгах? Какие фактические min/max и комиссии? Макетный курс и лимиты нельзя зашивать в продукт.
- **[OPEN]** ALT.VU как пункт пополнения показан в списке, но отдельный входящий сценарий и ограничения не документированы PNG полностью.

#### C. Вывод в сеть

- **[PNG]** Варианты USDT и USDC, выбор сети, адрес получателя (ввод/вставка/сканирование/книга), сумма с MAX, отображение ожидаемого получения и комиссии.
- **[PNG]** В книге адреса сохраняются с пользовательским именем и сетью; при создании показано подтверждение PIN. Один и тот же адрес в зависимости от сети не означает один и тот же маршрут вывода.
- **[INFER]** Нужны проверки допустимости пары актив+сеть, формата адреса, достаточности доступного остатка, комиссии и повторного подтверждения перед отправкой.
- **[OPEN/P0]** Откуда списывается сумма, при каких состояниях она резервируется, каковы минимумы/максимумы, финальность, отмена, ошибочный адрес, неверная сеть и idempotency? Это нельзя восстановить по статическим кадрам.

#### D. Внутренний перевод ALT.VU

**[PNG]** Вывод → ALT.VU → email или телефон получателя → результат поиска. Если найден, показывается частично скрытый email, имя и ввод суммы; если не найден, выделена ошибка и приглашение в ALT.VU. Далее экран «Проверьте перевод» с получателем, комиссией и суммой списания → PIN кошелька → подтверждение отправки → успешный результат → детали у отправителя (минус) и получателя (плюс), ID и квитанция.

**[PNG]** На этом макете текст утверждает «сразу и без комиссии» и что перевод нельзя отменить. Это **обещание конкретного дизайна**, не гарантия реализации и не повод без проверки назначать backend значение fee=0.

**[OPEN/P0]** Поиск по каким идентификаторам поддерживается реально? Как предотвращаются переводы не тому человеку, self-transfer, двойное нажатие, повтор транзакции, перевод на заблокированный/непроверенный аккаунт и невозможность исполнения после подтверждения?

#### E. Карты — общая модель, выпуск, тарифы, лимиты

- **[PNG]** Существует выбор нескольких карт и как минимум двух вариантов отображения: карусель и список. В листе мультикарты сказано «до 5 карт на один счёт» и «все платят с общего баланса». Карта имеет индивидуальное имя, реквизиты, подтверждения, Apple Pay/Google Pay, онлайн-оплату, тарифы, freeze, перевыпуск, закрытие.
- **[PNG]** Экран выпуска дополнительной карты предлагает оплату с доступного счёта или отдельными активами; доступность и цена зависят от выбранного типа в макете. При достижении 5 карт показан запрет новой до закрытия одной из имеющихся.

#### H. Партнёрская программа

**[PNG]** Пользователь делится кодом/ссылкой, приглашённый регистрируется, выпускает карту и совершает операции; реферер видит количество приглашённых, заработанное и **отдельный партнёрский баланс**. Кнопка «Зачислить на карту» предполагает перевод из партнёрского остатка в основной расходный контур. Макет рекламирует 30% от комиссии приглашённого.

**[OPEN/P1]** База начисления, допустимые операции, уровни, период, округление, условия выплаты, возвраты/аннулирование и доступность вывода без карты неизвестны. Процент не считать подтверждённым тарифом.

### 11.5. Баннерная система (лист от 07.11)

**[PNG]** Каталог содержит **12 кандидатов на одно место**, в порядке: (1) адрес доставки пластика; (2) активация пластика; (3) выпуск карты; (4) Apple/Google Pay; (5) добавить на главный экран; (6) биометрия; (7) push; (8) Telegram; (9) установка приложения; (10) адресная книга; (11) отзыв Trustpilot; (12) партнёрская программа. У каждого указаны сегмент, условие исчезновения, CTA. В подписи листа есть правило «каждый новый вход — следующий актуальный по кругу»; оно относится к конкретной предложенной конфигурации макета.

**[INFER]** Баннер не должен показываться, когда его целевое действие уже выполнено. Для нескольких подходящих баннеров нужен детерминированный приоритет и сохранение прогресса обхода; для неподходящих — пропуск в очереди.

**[OPEN/P0]** Был ли этот порядок утверждён? На стороне клиента или backend рассчитываются eligibility, impression, cap, очередь и завершение? Что делать если два баннера конфликтуют по условиям? Не превращать очередность из PNG в продакшен-алгоритм без решения.

### 11.6. Сквозные зависимости и опасные противоречия

1. **USD / USDT / USDC / RUB** — **единый баланс в USD подтверждён пользователем**. Приём токенов и RUB не доказывает отдельных счетов, курса 1:1 или отсутствия конвертации. Всё ещё нужен контракт FX, зачисления, доступности и округления.
2. **Доступ до KYC** — пользователем подтверждено: **все пополнения, исходящие переводы и выпуск карты заблокированы до успешного KYC**. Скриншоты допускают «Позже» и показывают продолжение после входа; не блокировать автоматически всю главную. Доступность других функций остаётся [OPEN].
3. **Карта до активации** — виртуальная и физическая карты, онлайн-оплата, Apple/Google Pay и блокировка имеют разные зависимости; наличие кнопки не доказывает доступность действия.
4. **Мультикарта и общий счёт** — утверждение «до 5» обнаружено в одной поздней итерации; более ранние варианты/тарифы могут описывать другую модель.
5. **P2P «мгновенно» и «бесплатно»** — текст UX не гарантирует успешный backend перевод без pending/failed; их нужно обрабатывать.
6. **Курс СБП** — на форме есть таймер, в результате показывается курс; не принимать отправку в банк за фиксацию/оплату.
7. **Активация пластика** — номер физической карты проверяет факт соответствия заказу, а PIN карты создаётся отдельно; не использовать PIN входа вместо issuer PIN.
8. **Реферальный баланс** — показан отдельным и с CTA зачисления на карту; не прибавлять автоматически к доступному кошельку.
9. **Баннеры** — один слот и очередь из 12 — вариант макета; фактическая логика не подтверждена.
10. **История** — карта, входящие активы и P2P требуют разных наборов полей, хотя отображаются в одной ленте.

### 11.8. Контракт работы над новым сценарием

До рисования нового экрана агент должен зафиксировать:

1. **Сущность и действие:** какая операция / карта / заказ изменяется; какой ID/тип/сеть/валюта.
2. **Actor и доступ:** страна, KYC, баланс, лимит, статус карты, платформа.
3. **Источник:** прямой PNG и версия; компонентная библиотека отдельно от продуктовой логики.
4. **Маршрут:** вход → форма → проверка → безопасность → pending → success/fail/cancel → история и back.
5. **Данные:** отображаемая и исходная валюты, сумма, fee, FX, округление, источник, доступный остаток, idempotency.
6. **Неизвестное:** явно [OPEN]; в моках использовать условный сценарий, не приписывать его API.
7. **Тесты:** успешный поток, ошибка ввода, недостаток средств, неподходящая сеть/карта/KYC, внешний возврат/таймаут, двойной submit, пустой список, отмена, восстановление.

**Критерии завершения реконструкции:** карта навигации раздела 2 и каталог раздела 4 покрывают известные экраны; раздел 11 задаёт модель данных и сквозные условия; P0-вопросы имеют подтверждённые ответы из продукта/API. **На 2026-11-12 подтверждены единый USD-баланс и KYC-gating всех пополнений, исходящих переводов и выпуска; актуальная версия карточных сценариев не определена:** документ пригоден для прототипов, но не является утверждённой бизнес-спецификацией.

**Область проверки этого дополнения:** прямой визуальный разбор перечисленных выше ключевых листов плюс каталог папок и существующая реконструкция разделов 1–10. Не выполнялась попиксельная ревизия каждой версии светлой/тёмной темы, вариантов анимаций и всех PNG из вложенных папок.

**Точное правило для мока:** `canTopUp = kyc === 'approved' && otherTopUpEligibility`; `canTransfer = kyc === 'approved' && otherTransferEligibility`; `canIssueCard = kyc === 'approved' && otherCardEligibility`. Здесь `approved` — **внутреннее имя состояния прототипа**, а не реальный backend enum. Если статус KYC не определён, считать операцию недоступной, пока проверка не подтвердит разрешение. Проверки выполняются не только в UI, но и на backend — при реализации.

**Не путать блокировку до KYC и отсутствие функции в релизе.** Кнопка может присутствовать, но быть недоступной с пояснением «Для переводов и выпуска карты пройдите проверку личности». Точные UX-тексты и способ входа в KYC ещё не согласованы.

### 12.2. Что осталось уточнить, без придумывания правил

1. **Решено (DEC-005):** любые пополнения общего USD-баланса **требуют успешного KYC**, включая СБП, USDT и USDC. До KYC метод не должен позволять инициировать пополнение. Поведение уже отправленных средств после изменения KYC-статуса остаётся открытым вопросом.
2. **P0:** какие версии карточного выпуска/активации утверждены; какие типы карт реально доступны? Пользователь ответил «не знаю»: не подменять этот ответ выбором по дате.
3. **P0:** схема хранения USD, FX, hold, refund, комиссии и реальная модель операции.
4. **P1:** партнёрский баланс показан отдельно как **не зачисленные ещё вознаграждения**. Нужно подтвердить, что он не является вторым расходным USD-счётом и когда становится доступным.
5. **P1:** статус KYC при истечении срока, повторной проверке, запросе дополнительных документов и отказе; допустимость исходящих операций в этих состояниях.
