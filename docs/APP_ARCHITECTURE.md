# alt.vu — карта приложения и руководство по сборке экранов

> **Статус:** рабочая реконструкция по PNG-макетам и библиотеке HTML/CSS. **Не** утверждённая продуктовая спецификация и **не** описание реализованного backend/API.  
> **Дата анализа:** 2026-11-11. **Библиотека:** снимок веб-сборки от 2026-11-10 18:18, исходный коммит `ae501917`.  
> **Платформы:** веб-кошелёк / мобильный web / PWA-контекст; отдельно Telegram Mini App. Native iOS/Android **не входят** в библиотеку.

## 0. Цель и критерии приёмки

Цель — дать дизайнеру, разработчику и AI-агенту ориентир, как собирать интерфейсы из `components/*.html`, согласовывать их с PNG и не домысливать продуктовую логику.

Результат считается пригодным **для прототипирования**, если:
1. Новый экран имеет источник PNG, название, точку входа, состояния, переходы и состав компонентов.
2. Для каждого переиспользуемого элемента указан реальный путь `components/<id>.html`; отсутствующие элементы помечены как новые.
3. В светлой/тёмной темах используется существующая система CSS, а не произвольно созданные стили.
4. Реальные бизнес-ограничения, роли, статусы, суммы и API **не выводятся** из демонстрационных значений на PNG.
5. Неизвестные решения оформляются как вопросы/допущения, а не как готовые требования.
6. Результат проверяется на 390 и 1440 px, с загрузкой ресурсов и без ошибок JavaScript; для состояний есть скриншоты или иная проверяемая фиксация.

**Легенда достоверности:** **[PNG]** — виден на макете; **[LIB]** — представлен в библиотеке; **[INFER]** — реконструкция пользовательского перехода, требующая проверки; **[OPEN]** — продуктовый вопрос не разрешён. Названия возможных маршрутов ниже — **смысловые идентификаторы документа**, не фактические URL.

## 2. Информационная архитектура

### 2.1. Общая схема [PNG + INFER]

~~~text
Вход в продукт
├── Регистрация: email → код → имя → создание/повтор PIN → готово
├── Вход существующего пользователя → подтверждение → PIN/сессия
└── Необязательная / отложенная подготовка к карте
    ├── Телефон → SMS/Telegram-код
    ├── Страна проживания → документ → проверка KYC
    ├── Пополнение доступного остатка
    └── Выпуск карты → ожидание → карта готова

Авторизованный кошелёк
├── Главная (баланс, карта/заглушка, быстрые действия, история, баннер)
│   ├── Пополнить
│   │   ├── СБП → банк → RUB/курс → приложение банка → ожидание → результат
│   │   ├── USDT / сеть → QR и адрес → отслеживание зачисления
│   │   ├── USDC / сеть → QR и адрес → отслеживание зачисления
│   │   └── ALT.VU → внутренний перевод [наличие пункта по макетам]
│   ├── Вывести
│   │   ├── USDT / сеть → адрес и сумма → проверка → PIN → статус
│   │   ├── USDC / сеть → адрес и сумма → проверка → PIN → статус
│   │   └── ALT.VU → поиск получателя → сумма → проверка → PIN → готово
│   ├── Заработать → партнёрская программа
│   ├── История → фильтры / детали → квитанция
│   └── Карта → выпуск / управление / тарифы / лимиты / пластик
├── Профиль → данные / настройки / адресная книга / безопасность
├── Уведомления / поддержка
└── Установка приложения (PWA-подсказки)

Telegram Mini App [отдельный контекст]
├── Приветствие / связь с Telegram / существующий аккаунт
├── PIN / блокировка / повторное создание / отвязка
├── Главная, профиль, партнёрка
└── KYC / статусы / операции — доступность уточняется
~~~

**Навигация:** в `components/bnv.html` есть нижнее меню из **«Главная / Пополнить / Карта / Вывести / Профиль»** [LIB]. Однако PNG демонстрируют и варианты с быстрыми действиями без постоянно видимого нижнего меню. Универсальное правило показа навигационной панели **не подтверждено** [OPEN]. Профиль на некоторых экранах открывается нажатием на имя/аватар; уведомления и поддержка — отдельными кнопками в шапке [PNG].

## 3. Каркас и композиция экранов

1. **Типы экранов:** главная с собственной шапкой и крупной карточкой; стандартный экран с «назад» и заголовком; полноэкранный статус; шторка поверх предыдущего экрана; форма с нижним основным действием; детальная карточка операции. [PNG]
2. **Шапка:** `hdr` для главной, `head` для обычных экранов; кнопки уведомлений/поддержки показаны в шапках отдельных макетов. Вопрос: какие иконки глобальны, а какие контекстны.
3. **Основное действие:** `btn` — лайм, обычно одно доминирующее CTA на экран; `btno` — вторичное; `lnk` — текстовая ссылка. Состояния disabled, ошибка и загрузка не тождественны друг другу.
4. **Плиты/строки:** `rows`, `tbl`, `fld`, `amount`. Значение, подзаголовок, иконка, статус и правая стрелка имеют семантику; не подменять их произвольными контейнерами.
5. **Шторки:** `sheet`, `netsheet` и их затемнение/handle; контент меняется по задаче. Не все шторки собраны в библиотеке; «выбор банка», фильтры и PIN — разные композиции.
6. **Темы:** светлая — переменные на `.phone`, тёмная — `html.dark`. Тестировать обе. Не переносить `showcase/specimen.css` и `showcase/states.css` в продукт: это стили демонстрационной витрины.
7. **Ресурсы:** использовать `assets/`; не рисовать логотипы монет/сети вручную, когда существует оригинальный asset. Типографика — Inter из библиотеки.
8. **Responsive:** мобильная ширина и десктопная рамка — разные контексты. Папка `десктоп` показывает центрированную презентацию телефона внутри браузера; она не доказывает наличие полноценного широкого web-layout.
9. **Статусы:** экран загрузки, ошибка, ожидание внешнего действия и успешный результат — отдельные экраны/состояния, а не одна иллюстрация. `done`, `toast`, `warn` и `bdg` помогают их собрать.

### 4.1. Реконструированные сценарии (проверяемые PNG)

**A. Регистрация / онбординг:** email → код → имя → создание и повтор PIN → созданный кошелёк. Отдельный пошаговый сценарий «Три шага до карты»: телефон → код → страна проживания → документ/проверка → пополнение → выпуск → готово. В показанном сценарии отдельные шаги можно отложить, пользователь возвращается к ним позже [PNG]; точные условия «Позже» и поведение при незавершённом KYC — [OPEN].  
Референсы: [регистрация — сентябрь](https://drive.google.com/drive/folders/1ssuL2A6j6Tay8rjx_4bj3dWoYh3EByeg), [путь пользователя](https://drive.google.com/drive/folders/1aMV5EebpkhodzWGjylDPH1QJ-hhbmA11), [полный лист пути](https://drive.google.com/file/d/14DPIIJJZrVsbsnsTptLuZ6Tea08SCVjS/view).

**B. Главная:** шапка/аватар → карточка с балансом или placeholder карты → быстрые действия → системный баннер (при наличии) → короткая история и «Все». ### 6.1. Несовпадения, которые нельзя «исправлять» по догадке

1. **Главная:** в папке с «ЭТАЛОН» есть тёмное лицо карты; в библиотеке и других листах — лаймовые/зелёные варианты. Нельзя переносить «эталон» на все карточные экраны без решения.
2. **Текущая навигация:** компонент нижнего меню демонстрирует 5 разделов, но на части PNG навигация другая или не показана. Нет подтверждённого правила постоянного отображения.
3. **Тарифы / число карт / выпуск:** среди макетов существуют разные значения, скидки, варианты платёжных сценариев и multi-card. Числа не являются константами приложения.
4. **Веб и Telegram:** сходство экранов не подтверждает равенство фичей, способов входа и доступных операций.
5. **Исторические скриншоты и действующая сборка:** PNG показывают проекты и состояния по датам; `README.md` относится к конкретному снимку CSS. Эти источники не синхронизированы автоматически.

## 7. Состояния и переходы: минимальный контракт для каждого экрана

Для каждого сценария описывать:
- **Entry** — откуда пришли; параметры (тип операции, монета, сеть, recipient ID, card ID).
- **Eligibility** — допустимость действия: KYC, средства, лимиты, доступность метода, платформа.
- **Loading / empty / ready / invalid / submitting / pending / success / failed** — не обязательно все, но явно отметить применимые и отсутствующие.
- **Exit** — «назад», закрытие шторки, отказ, повтор, переход к деталям или на главную.
- **Data** — названия полей, форматы/маски, источник данных, отображаемая валюта, точность и локализация.
- **Effects** — что происходит после CTA: запрос, редирект в банк, PIN, изменение баланса, история; если API неизвестен, обозначить mock.
- **Recovery** — потеря сети, устаревший курс, повторное открытие, двойное нажатие, прерванный платёж, открытие после перезагрузки.
- **Tracking** — события аналитики, если продукту нужны: показ, шаг, ошибка, завершение; сейчас [OPEN].

Предварительная модель операций: `draft → validating → awaiting_confirmation → processing → succeeded | failed | cancelled`. Это **только предлагаемый словарь для проектирования**, не доказанные значения backend. Для СБП отдельно нужны ожидание перехода/оплаты/зачисления; для криптопополнения — ожидается сеть и подтверждения; для P2P — lookup и проверка получателя.

## 8. Указания AI-агенту по сборке прототипов

1. **Зафиксируй основание:** конкретный PNG/папка, дата итерации, желаемая платформа, сценарий и начальное состояние. Если не задано — выбирай самый близкий явно названный референс; неопределённость отметь в README экрана.
2. **Разложи экран на блоки:** status/safe area, header, hero/card, summary, content rows/form, sticky CTA, overlay/modal, feedback. Таблицу «блок → `components/<id>.html` → новый блок» составить **до** верстки.
3. **Сначала композиция:** используй исходные классы и DOM паттерны. Не создавай новые визуальные стили, пока отсутствующий блок не выявлен явно. Для отсутствующего блока сделай отдельный компонент и опиши, почему нет подходящего образца.
4. **Не переноси витрину в продукт:** `showcase/` служит только для демонстрации и не определяет поведение реального кошелька; допустимо использовать существующую HTML-витрину как reference.
5. **Интерактивность прототипа:** все видимые кнопки должны иметь ожидаемое действие (переход, mock state, валидация, закрытие, popup). В прототипе должна быть возможность воспроизвести минимум success, error, loading, disabled и empty там, где они применимы.
6. **Содержимое:** демонстрационные ФИО, адреса, деньги и карты — фикстуры; не размещать реальные пользовательские данные, токены, PAN/CVV или секреты.
7. **Техническая проверка:** локальная витрина; 390 и 1440 px; светлая/тёмная тема; console/pageerror/requestfailed; переполнения, видимость CTA, модальные перекрытия, скролл, клавиатура, изображения/шрифты.
8. **Результат:** исходный PNG, список исходных компонентов, список новых блоков, список известной/предполагаемой логики, скриншоты до/после и нерешённые вопросы. Не утверждать соответствие продакшену только по внешнему виду.
9. **Безопасность репозитория:** новые прототипы помещать в отдельную папку (например, `prototypes/<flow-name>/`), не трогать `components/` и `css/alt-vu-wallet.css` без явного согласованного изменения библиотеки.
10. **Регрессия:** запускать `python3 build/check.py --no-png` при наличии Playwright. Скрипт рассчитан на `file://`; если среда запрещает локальные file-URL, зафиксировать блокировку, а не объявлять тест пройденным. Отдельный тест по HTTP не равен успешному выполнению оригинального скрипта.
