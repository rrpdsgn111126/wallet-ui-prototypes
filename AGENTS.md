# AGENTS.md — alt.vu

**Единственная точка входа для AI-агента.** Репозиторий: `rrpdsgn111126/wallet-ui-prototypes`, ветка `main`. Прежде чем действовать, прочитай этот файл; дополнительные документы открывай **по задаче**, а не все подряд.

## 1. Единственный прототип

- Действующий прототип: [`transfi-remittance/index.html`](./transfi-remittance/index.html), связанные банковские экраны: [`transfi-remittance/legacy.html`](./transfi-remittance/legacy.html).
- Все UX/UI-изменения выполнять только в `transfi-remittance/` и необходимых зависимостях. Не создавать `v2/v3`, альтернативные HTML-копии или новые каталоги прототипов.
- `ui-kit/` и `components/` — референсная библиотека, а не самостоятельный второй прототип; её примеры должны оставаться согласованными с действующей реализацией.
- Репозиторий предназначен только для сборки и проверки фронтенд UX/UI-прототипов. Backend, API-интеграция, платёжная инфраструктура и технический план внедрения не входят в область работы.
- Все данные и ответы провайдера имитируются локальными mock/fixtures. Не отправлять реальные платежи, не подключать платёжные API, секреты или production-данные.

## 1.1. Изоляция рабочих веток (решение 18.11.2026)

- `main` — стабильный опубликованный прототип. Новые UX/UI-изменения, токены и компоненты сюда **не переносить без явного согласования пользователя**.
- `work/prototype` — единственная рабочая ветка дальнейших изменений прототипа. Работать в прежнем `transfi-remittance/`, не создавать новую папку или дублирующий HTML-прототип.
- `work/design-system` — независимая рабочая ветка дизайн-системы и её проверки. До согласованного объединения её CSS/токены **не переносить** в `main` или `work/prototype`.
- Не выполнять merge, cherry-pick или другие переносы изменений между этими тремя ветками без отдельного указания пользователя. Каждую ветку тестировать отдельно.
- GitHub Pages по основному URL публикует `main`. Ссылка на этот URL **не является предпросмотром рабочих веток**; наличие отдельного preview подтверждать отдельно.
- Исключение для публикации: `preview/design-system/` в `main` — только изолированные **статические артефакты** из `work/design-system`, синхронизируемые workflow `.github/workflows/publish-design-system-preview.yml` из рабочей ветки. Этот каталог не подключать к основным экранам `main` и не считать слиянием исходных токенов или компонентов. Его ссылки: `preview/design-system/transfi-remittance/` и `preview/design-system/ui-kit/`.

## 3. Приоритет источников

1. Последнее явное требование пользователя и подтверждённые решения о продукте.
2. `APP_ARCHITECTURE.md` — правила продукта и UX-сценариев.
3. `UI_PATTERNS.md` — правила композиции и визуального поведения.
4. Действующий DOM/CSS/JS и образцы библиотеки — **фактическое поведение кода**, которое нужно проверить до редактирования, а не замена продуктовым требованиям.
5. Старые PNG, архивные версии и гипотезы — только при явной необходимости.

При конфликте выяснить область действия и дату/статус решения. **Не переносить неподтверждённые API-гипотезы в продуктовые факты.** Указывать расхождения между актуальными правилами и реализованным кодом.

## 4. Обязательная последовательность UI-задачи

1. Определить затрагиваемые сценарии/экраны и необходимые источники по таблице выше. Для нового экрана зафиксировать актуальный референс (PNG/работающий экран), его версию, исходное состояние и карту «блок → библиотечный компонент».
2. **До новой реализации** найти существующий компонент, классы, токены, обработчики и сравнимый экран. Зафиксировать, что переиспользуется.
3. Менять только необходимый общий компонент или конкретный экран; не копировать его в альтернативный прототип. Не менять смежную логику без явного основания.
4. В интерактивном прототипе проверять реальные переходы, back/Escape, focus, overlay, scroll, состояния CTA, success/fail/pending и отсутствие JS-ошибок в пределах затронутого сценария.
5. Проверять в Playwright релевантные `tests/bank-qa/smoke.py`, `tests/bank-qa/source-flows.py`, `tests/bank-parity.mjs` и иные существующие тесты. Минимум — мобильные 390/430 px; desktop 1440 px при изменениях компоновки. Если среда не позволяет запуск, явно сообщить об этом.
6. Проверить итоговый commit и опубликованную GitHub Pages-страницу; не заявлять об успешном деплое только по факту изменения файла.
7. В результате назвать изменённые пути, commit, проверки и неразрешённые проблемы. Для визуальных изменений сравнить до/после; неподтверждённое соответствие не заявлять.

При отсутствии доступа на запись в GitHub запросить его в начале задачи. Не утверждать, что изменения опубликованы, пока commit и доступность страницы не проверены.

## 5. Поддержка документации

- Если изменяется **продуктовое/UX-правило**, обновлять только `APP_ARCHITECTURE.md`.
- Если изменяется **общий визуальный/интерактивный паттерн**, обновлять только `UI_PATTERNS.md` и соответствующий референсный компонент.
- Если изменяются принципы работы, источники или маршрутизация, обновлять `AGENTS.md`.
- **Одно правило — один нормативный документ.** Старое правило заменить по месту; историю решения хранит Git, не дублировать хронологические поправки в конце других документов.
- Не удалять уникальные требования при консолидации. При необходимости сохранять прежние редакции через Git history.
